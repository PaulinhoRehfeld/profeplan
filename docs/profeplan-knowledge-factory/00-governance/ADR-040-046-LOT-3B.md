# ADRs propostas — Lote 3B

Data: 7 de agosto de 2026.

Status geral: **propostas — aguardando aprovação humana**.

Estas ADRs complementam ADR-033 a ADR-039 e não as substituem.

## ADR-040 — Adapters Supabase recebem client por injeção

**Status:** proposto

`@profeplan/knowledge-factory-supabase` será o pacote concreto de infraestrutura.

O pacote:

- não lerá `process.env`;
- não importará `api/_lib/supabaseAdmin.ts`;
- não criará credenciais;
- não conhecerá project ref de produção.

Clients serão construídos no composition root e injetados.

`@supabase/supabase-js` será dependência runtime explícita do pacote, alinhada à versão já adotada no monorepo.

Consequência: `api/` pode reutilizar o `supabaseAdmin` existente sem inverter dependências.

## ADR-041 — Contextos Supabase privilegiado e requester são separados

**Status:** proposto

O Lote 3B distinguirá:

- **System context**: client server-side privilegiado para corpus global e auditoria;
- **Requester context**: client autenticado sob identidade do usuário para operações privadas sujeitas a RLS, especialmente OPP.

`service_role` não será o padrão para operações privadas do professor.

Consequência: RLS permanece defesa em profundidade em fluxos requester-scoped.

## ADR-042 — Escritas multi-tabela não usarão pseudo-transações

**Status:** proposto

Chamadas Supabase independentes não serão tratadas como transação.

Operações logicamente indivisíveis, como:

- componente + versão + links;
- OPP + evento;

serão bloqueadas até existir função SQL/RPC transacional ou outra fronteira atômica comprovada e aprovada.

Nenhuma RPC é autorizada por esta ADR antes de migration/testes/rollback específicos.

## ADR-043 — Erros Supabase/PostgreSQL são traduzidos na fronteira do adapter

**Status:** proposto

O pacote definirá erro de persistência estável e sanitizado.

SQLSTATE, PostgREST codes, queries e mensagens internas não atravessarão a porta para domínio/API/UX.

Métodos `find*` que admitem ausência continuarão retornando `null`.

## ADR-044 — Observabilidade de persistência é injetada

**Status:** proposto

Adapters não dependerão diretamente de `@profeplan/logger` no primeiro PR.

Motivo: o logger atual é Node-specific e escreve em filesystem de forma síncrona.

O adapter receberá interface mínima de logging estruturado; o composition root poderá adaptá-la ao logger existente.

Logs devem conter operação, duração, aggregate/correlation e outcome, sem secrets nem conteúdo pedagógico bruto.

## ADR-045 — Primeiro PR 3B implementa somente AuditRepository

**Status:** proposto

A primeira fatia será:

`AuditRepository ↔ public.kf_audit_events`

Motivos:

- uma tabela;
- porta completa;
- append-only;
- sem transação multi-tabela;
- sem mudança de contrato;
- prova client injection, mapper, erro, observabilidade e CI descartável.

Nenhuma segunda porta será incluída no mesmo PR.

## ADR-046 — Lookup de currículo ativo deve incluir etapa

**Status:** proposto

A porta atual `findActivePackageByState(state)` é incompatível com o schema físico, que permite um pacote ativo por `(state, stage)`.

Antes do adapter curricular deverá ser aprovada alteração equivalente a:

`findActivePackage(state, stage)`

Nenhuma modificação em `@profeplan/knowledge-factory` é autorizada nesta definição documental.
